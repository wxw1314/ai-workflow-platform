# 电商智能经营分析与决策 Agent — 功能级开发计划

本目录将六周总规划拆分为可独立交给 Codex 执行和验收的功能计划。**每个功能一个 Markdown 文件**，按周组织。执行时一次只处理一个文件，不要让 Codex 跨文件顺手重构。

## 使用顺序

1. 先执行 `00-项目总览/00-项目范围与执行约定.md`。
2. 按 `01-第1周` 到 `06-第6周` 顺序推进。
3. 每个功能开始前，让 Codex 阅读对应计划和相关现有代码，先给出差异分析与实施方案，再修改。
4. 每个功能完成后，补齐测试、运行结果和文件末尾的验收记录。
5. 遇到计划外的架构变更、外部平台写操作、权限模型变化，先停下来更新计划，不要直接扩大范围。

## 目录

- `00-项目总览/`：项目边界、通用安全约束、功能计划模板。
- `01-第1周-盘点与建模/`：现状审计、业务边界、领域模型和模块边界。
- `02-第2周-自有经营数据/`：商品、订单、指标、库存、促销、演示数据。
- `03-第3周-竞品数据/`：竞品关联、导入、数据源适配、快照、变化分析。
- `04-第4周-经营分析Agent/`：证据结构、查询工具、确定性分析、RAG、LangGraph、报告。
- `05-第5周-定价审批与监控/`：定价情景、审批、受控执行、审计、监控与通知。
- `06-第6周-前端评测与交付/`：工作台、业务页面、Agent UI、审批 UI、评测、安全验收、文档。

## 全局执行原则

- 以当前仓库为准核对实现；已有 FastAPI、SQLModel、PostgreSQL、LangGraph、RAG、Milvus、SSE、Checkpointer、重试、取消、Langfuse 和 React 页面优先复用，不重建。
- PostgreSQL 存业务事实、状态和历史快照；Milvus 只做非结构化知识语义检索。
- LLM 不直接访问数据库、不生成任意 SQL；通过有限白名单业务 Service/Tools 获取数据。
- 关键数值由确定性 Python 代码计算；LLM 负责理解、规划、综合和表达。
- 竞品数据必须记录来源、采集时间和授权依据；不可观测的竞品销量、利润、库存不得编造。
- 模拟数据必须明确标注为 demo/mock，不得包装成真实客户数据。
- 所有业务对象执行租户/用户 ownership 校验；前端隐藏按钮不构成权限控制。
- 任何影响外部业务状态的写操作（调价、发布促销、批量通知等）必须经过服务端持久化人工审批。审批前只能创建请求，不能执行。
- 审批通过后仍需重新校验操作者权限、目标对象、参数、当前数据版本/状态、payload hash、过期时间和幂等键。
- 不把 Langfuse Trace 当作业务审计日志；审批与执行审计必须落 PostgreSQL。
- 不为了炫技先做 Multi-Agent；第一版以一个可靠的 LangGraph Agent 为目标。


## 项目计划与规范

项目开发计划统一存放在 `plan/` 目录。

开始开发任务时：

1. 阅读 `plan/README.md`，了解整体计划。
2. 阅读 `plan/00-项目总览/00-项目范围与执行约定.md`，
   遵循项目范围和执行流程。
3. 涉及安全、权限、数据库、Agent Tool、
   RAG、文件上传或人工审批时，
   必须遵循 `plan/00-项目总览/01-通用安全与边界规范.md`。
4. 根据当前任务读取对应的 `EC-xxx.md` 功能计划。
5. 不要每次都读取所有功能计划，只读取当前任务相关文件。
6. 新增功能计划时，参考
   `plan/00-项目总览/02-功能计划文件模板.md`。
