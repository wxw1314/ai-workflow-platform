# 电商领域 ERD 与数据库约束

- **计划 ID：** EC-003
- **所属阶段：** 第1周
- **优先级：** P0
- **依赖：** EC-002
- **状态：** 未开始

## 1. 目标与用户价值

设计最小可用数据模型和约束，保证业务事实可追溯。

## 2. 功能范围

### 本次包含
- 设计核心表关系、主外键、索引、唯一约束。
- 设计 tenant/user ownership。
- 设计时间快照与幂等字段。
- 明确金额 Numeric/Decimal、币种和 UTC 时间。

### 本次不包含
- 不重建现有 FastAPI、Agent、RAG、SSE、Checkpointer、Milvus 或前端基础设施。
- 不实现本文件未列出的相邻业务功能。

## 3. 现有能力复用与代码检查

先检查现有 SQLModel 模型和迁移；避免重复表、冲突命名和破坏既有表。

Codex 必须先检查当前仓库真实代码、模型、路由、迁移和测试；不得凭计划臆造文件路径或重复造轮子。

## 4. 数据与接口

ERD、字段说明、迁移方案和索引说明。

## 5. 业务规则与边界条件

快照不可被覆盖成“当前值”；同一来源同一采集批次需可去重；删除策略需考虑审计和关联数据。

## 6. 安全、权限与隐私

数据库约束不能替代 API 权限校验；租户字段应进入查询条件和必要索引。

## 7. 人工审核 / 人工介入

审批/审计模型只定义必要字段，具体状态机在第5周实现。

## 8. 异常与恢复

迁移失败需可回滚；不允许在生产数据上无备份执行破坏性迁移。

## 9. 测试要求

检查 FK、唯一约束、索引、金额精度、跨租户查询和迁移升级/降级。

## 10. 验收标准

ERD 覆盖 MVP，迁移策略明确，约束能防止重复和跨租户关联。

## 11. Codex 执行约束

1. 先只读检查并汇报现状、差异、拟修改文件和风险。
2. 等待确认后，仅实施本计划范围。
3. 先补测试，再实现或同步实现；不得删除已有测试来通过检查。
4. 不得修改自动生成的 OpenAPI SDK 文件；如 API schema 变化，按项目既定流程重新生成。
5. 汇报实际修改文件、迁移、测试命令和真实测试结果。
